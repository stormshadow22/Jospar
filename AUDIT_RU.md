# Проверка проекта Jospar — новая версия 2.1.0

Дата: 2 ноября 2026 года.

## Результат и границы работы

Новая версия находится в `Jospar-firebase-spark-v2`. Файлы приложения в исходной соседней папке `Jospar-firebase-spark` не редактировались. Повторная проверка подтвердила совпадение всех 69 сохранённых хешей. Для первой версии сохранён перечень SHA-256 в `docs/V1_SOURCE_MANIFEST.json`; он фиксирует состояние исходников на момент подготовки отчёта, а не историю до начала работы.

Проверены клиент планировщика, облачный адаптер, профиль и чат, правила Firestore, локальный сервер, push-worker, сборка, зависимости, существующие тесты и оформление на снимках. Изменения направлены на найденные ошибки; общий дизайн и существующие функции сохранены.

Это проверка доступного кода и локальных сценариев. Она не означает отсутствие любых возможных ошибок и не подтверждает состояние работающего Firebase-проекта. Deployment, рабочая база, письма, SMS и FCM в этой работе не использовались.

## Что исправлено

### 1. Перезапись чужой записи push-устройства — высокий приоритет

**Было:** правило `pushDevices` при обновлении проверяло только UID в новых данных. Зная ID документа чужого устройства, другой подтверждённый пользователь мог перезаписать его своей записью. Это позволяло нарушить привязку/доставку уведомлений; получение чужого FCM-токена само по себе этим не доказывается.

**Стало:** обновление требует совпадения владельца существующей записи с текущим пользователем. Идентификаторы новых устройств дополнительно включают UID. Добавлена проверка попытки захвата документа и допустимого обновления владельцем на эмуляторе.

Файлы: `firestore.rules`, `public/cloud.js`, `tests/firebase-rules.cjs`.

### 2. Устаревший Admin API обходил текущие правила — высокий приоритет

**Было:** `JOSPAR_MODE=firebase` включал старые `/api/profile`, `/api/state`, `/api/account`. Они работали через Admin SDK и другую схему профиля. Удаление аккаунта не очищало публичный профиль, push-устройства и команды и не требовало недавнего входа. Такой путь противоречил текущему клиентскому удалению.

**Стало:** старый API отключён. Локальный сервер раздаёт сайт и `/api/health`; остальные `/api` возвращают 503 `eConfiguration`. Приложение уже использовало прямой Firebase SDK. Push-worker остаётся отдельной явно включаемой функцией.

Совместимость: внешние клиенты старого REST API, если они есть, потребуют отдельной миграции. В поставленном приложении вызовов этого API не найдено.

Файл: `server/index.js`. Серверные библиотеки действительно обходят правила Firestore — [документация Firebase](https://firebase.google.com/docs/firestore/security/rules-conditions).

### 3. Приглашения бывшего владельца оставались действительными

**Было:** после передачи команды старое приглашение продолжало давать право вступления, даже когда его автор уже не управлял командой.

**Стало:** принятие требует, чтобы автор приглашения оставался владельцем команды. Worker также проверяет актуального владельца перед уведомлением о приглашении.

Файлы: `firestore.rules`, `server/push-worker.js`. Проверено на эмуляторе.

### 4. Кириллические логины не согласовывались с правилами

При проверке на эмуляторе выражение `'Фархат'.lower() == 'фархат'` оказалось ложным. Старый клиент использовал JavaScript `toLowerCase()` для ID реестра, что могло расходиться с результатом Firestore Rules.

Новые профили сохраняют логин в нижнем регистре ещё на клиенте; правило создания запрещает заглавные/titlecase-символы. Отображаемое имя сохраняет написание пользователя. Старые профили не переименовываются. Добавлена проверка кириллической регистрации и запрета недопустимых логинов.

Файлы: `public/backend-firebase.js`, `firestore.rules`. Синтаксис строк и регулярных выражений: [Firebase Rules String](https://firebase.google.com/docs/reference/rules/rules.String).

### 5. Импорт и загрузка допускали повреждённые данные

**Было:** часть полей не проверялась либо преобразовывалась в строки неявно; встречались допустимые для старого валидатора массивы вместо строк, невозможные даты/время, повторяющиеся ID. Вложенные `null` могли выбрасывать исключения. Облачные данные перед входом не проходили полную клиентскую проверку.

**Стало:** проверяются типы, действительность дат и времени, ID и ссылки, метаданные, лимиты и опасные ключи объектов. Повреждённые данные отвергаются до отображения/редактирования. Импорт ограничен 650 000 байт до чтения; после асинхронного чтения проверяется, что аккаунт не сменился. Сервер и браузер используют одну реализацию валидатора.

Файлы: `public/validation.js`, `server/validation.js`, `public/backend-firebase.js`, `public/app.js`.

### 6. Выход мог обогнать сохранение

Выход и удаление аккаунта теперь ждут очередь сохранений. При ошибке сохранения предлагается сначала экспортировать изменения и повторить сохранение. Предупреждение при закрытии страницы учитывает незавершённые сохранения. Действия интерфейса и клавиатуры ограничиваются во время выхода. Пароль и код очищаются из состояния после успешного входа.

Файл: `public/app.js`.

### 7. Часть состояния переживала смену аккаунта

Очищаются черновик профиля и чата, состояние просмотра, undo, фильтр/поисковая строка, временные ошибки сохранения и pending-регистрация. Облачный кеш привязан к UID. Pending-регистрация больше не хранит пароль в своём объекте.

Файлы: `public/app.js`, `public/cloud.js`, `public/backend-firebase.js`.

### 8. Асинхронные операции могли обновлять уже закрытый чат

Добавлена проверка поколения сессии/запроса после ожиданий. Ответ загрузки старой команды не открывает её повторно после перехода в другую. Завершение отправки из одного чата не очищает черновик другого. Повторная отправка и повторные действия кнопок защищены от двойного выполнения.

Файл: `public/cloud.js`.

### 9. Удаление участника могло затереть параллельное вступление

Вместо сохранения устаревшей копии `memberIds` используется атомарный `arrayRemove` при удалении участника и выходе. Это сохраняет изменения списка участников, произошедшие параллельно.

Файлы: `public/cloud.js`, `src/firebase-client.js`.

### 10. Единственный владелец не мог завершить работу с командой

Теперь единственный участник-владелец может нажать «Закрыть команду». Документ превращается в недоступную архивную запись с пустыми `memberIds` и `ownerId`. Такой пользователь больше не блокируется проверкой участия при удалении аккаунта.

Сам документ намеренно сохраняется: физическое удаление корня оставило бы подколлекции, а повторное создание того же ID могло бы открыть старые сообщения. Архивную команду нельзя занять повторно. Проверено на эмуляторе.

Файлы: `public/cloud.js`, `firestore.rules`. Подколлекции не удаляются автоматически — [документация Firebase](https://firebase.google.com/docs/firestore/manage-data/delete-data).

### 11. При удалении аккаунта оставались дополнительные личные записи

Дополнительно очищаются старые `users/{uid}/devices`, исходящие приглашения и локальные копии/история аккаунта; уведомления удаляются пакетами. Проверено в браузере с подменой SDK. Worker не создаёт новое уведомление, если родительский документ пользователя уже отсутствует.

Ограничения сохранены отдельно ниже: удаление Firestore и Firebase Auth не является одной общей транзакцией.

### 12. CSV недостаточно защищался от формул

Экспорт теперь нейтрализует формулы с начальным пробелом/переносом строки и корректно экранирует кавычки. Добавлена проверка CSV с такими значениями.

Файл: `public/features.js`.

### 13. Автоматическая тема не восстанавливалась

Значение `auto` сохранялось в настройках, но при запуске подменялось светлой темой. Теперь оно учитывается. Подпись облачного режима также больше не показывает «Локальный режим» до первого сохранения.

Файл: `public/app.js`.

### 14. HTTP-ответы и кеширование

Локальный сервер возвращает 404 для отсутствующих файлов вместо HTML с кодом 200. JS/HTML перепроверяются браузером при загрузке; защитные заголовки добавлены также в конфигурацию Hosting. Эти заголовки вступят в силу на Hosting только после публикации.

Файлы: `server/index.js`, `firebase.json`.

### 15. Push-worker и зависимости

Ключ выполняемой задачи worker теперь включает полный путь сообщения: одинаковый ID в разных командах больше не подавляет вторую обработку. Для приглашений учитываются подтверждение email, отключённый аккаунт и текущий владелец команды.

Совместимым `npm audit fix --ignore-scripts` обновлены lockfile и зависимости. После обновления сервер: **0 известных уязвимостей**, клиентские production-зависимости: **0**. В полной цепочке инструментов разработки осталось **15 moderate**, включая транзитивные зависимости Firebase CLI. Результат относится к базе npm на дату проверки; это не доказательство отсутствия всех уязвимостей.

`npm audit fix --force` не применялся: он предлагал понизить Firebase CLI с 15.34.2 до несовместимой 13.11.2. Принудительные major-overrides также не добавлялись без проверки совместимости.

### 16. Переносимость проверок

Браузерные тесты больше не требуют исключительно `/usr/bin/chromium`: на Windows ищутся Edge/Chrome, поддерживается `CHROMIUM_PATH`. Добавлены команды `npm run test:browser` и `npm run test:rules`.

- `npm run build`: клиентский Firebase SDK и service worker собираются.

Firebase CLI сначала завершался из-за локальной ошибки Java/UnixDomainSockets. Прямой запуск эмулятора с `-Djdk.net.unixdomain.tmpdir=C:\Windows\Temp` позволил провести проверки. Инструкция воспроизведения добавлена в `FIREBASE_SETUP_RU.md`.

## Что ещё требуется и что не обещает эта версия

1. **Публикация и проверка на рабочем Firebase.** Новые правила не опубликованы. После их публикации старый клиент первой версии может больше не регистрировать логины с заглавными буквами: выпуск клиента и правил должен быть согласован. Перед выпуском нужны согласованный deploy клиента/правил, проверка провайдеров Auth, двух реальных аккаунтов и реальной доставки FCM. Копия использует тот же Firebase-проект, отдельная тестовая база автоматически не создавалась.
2. **Надёжная очередь push.** Worker по-прежнему отслеживает последние 100 событий. Долгий простой, высокая активность, перезапуск и события за этим окном могут приводить к пропускам. Нужны outbox/очередь, мониторинг, ограничение повторов и метрики доставки. Push не имеет гарантии exactly-once.
3. **Защита квот от злоупотреблений.** Подтверждённый пользователь может создавать много команд/сообщений/приглашений. Владение данными проверяется, но серверного rate limit для прямых Firestore-записей нет. Нужны оценка App Check, лимиты и наблюдение за квотами; одна клиентская блокировка кнопки этого не заменяет.
4. **Удаление истории и политика хранения.** Сообщения команд, документы прочтения и архивные команды физически остаются. После закрытия команды клиентский доступ закрыт. Нужен отдельный административный процесс очистки/анонимизации и понятная политика хранения. Подтверждение удаления аккаунта теперь сообщает о возможном сохранении сообщений.
5. **Согласованное удаление Auth + Firestore.** Между этими сервисами нет одной общей транзакции. Если последняя операция удаления Auth завершится ошибкой, очистка данных может уже произойти. Для строгой гарантии нужен доверенный идемпотентный процесс удаления с повторением и журналом статуса; текущий клиентский путь не даёт такой гарантии.
6. **Синхронизация и восстановление.** Одновременное редактирование планов на двух устройствах обрабатывается конфликтом версии без автоматического слияния. Есть экспорт и локальная резервная копия, но нет полноценного интерфейса восстановления копий и истории версий.
7. **Масштаб данных.** Личные планы хранятся одним документом и сохраняются целиком; действуют лимит приложения 650 000 байт и ограничение Firestore. Большие аккаунты потребуют разделения задач/привычек на документы, пагинации и миграции. В чате отображаются последние 100 сообщений без загрузки более старых.
8. **Оставшиеся зависимости разработки.** 15 предупреждений moderate в цепочке Firebase CLI требуют отслеживания совместимых обновлений. Production-цепочки на дату проверки чисты по npm audit.
9. **Локализация и доступность.** В облачных ошибках/подсказках остаются русские строки при выборе EN/ҚАЗ; полная локализация, контраст, screen reader и реальные мобильные устройства требуют отдельного прохода. Автотест ширины не заменяет такую проверку.
10. **Эксплуатация.** Нужны резервное копирование рабочей базы, минимальные IAM-права worker, проверка восстановления, управление секретами и журнал ошибок. Политика CSP пока не введена: её нужно согласовать с Firebase Auth/reCAPTCHA, встроенным скриптом конфигурации и текущими inline-стилями.

## Как продолжить

Для просмотра новой версии запустите `start-local.cmd` из новой папки. Для push используется `start-push.cmd` с вашим локальным `.env`. Подробности — в `README.md` и `FIREBASE_SETUP_RU.md`. Старую папку можно продолжать хранить как первую версию.
